# Research: Transactional Outbox (US-07)

Every decision below is final; nothing is left as NEEDS CLARIFICATION. Q1 = A (user): the US-03
dead-letter store and worker become the outbox and its relay.

## R1. Table: evolve `payment_dead_letters` into `payment_outbox`

**Decision**: one migration, `TurnDeadLettersIntoOutbox`, that does the following:

1. **Renames** the table `payment_dead_letters` → `payment_outbox` and these columns:

   | Old column | New column |
   |---|---|
   | `CreatedAt` | `RecordedAt` |
   | `NextRetryAt` | `NextAttemptAt` |
   | `ResolvedAt` | `PublishedAt` |

2. **Maps the statuses**:

   | Old status | New status |
   |---|---|
   | `PendingRetry` | `Pending` |
   | `Resolved` | `Published` |
   | `Exhausted` | `Exhausted` (unchanged) |

3. **Adds `EventId uuid`**, backfilled from the payload (`("Payload"->>'eventId')::uuid`; `Payload` is
   already `jsonb`), then sets it NOT NULL with a unique index.
4. **Adds `Sequence bigint GENERATED BY DEFAULT AS IDENTITY`**. Existing rows are backfilled in
   `RecordedAt, Id` order, then the identity is restarted after the maximum. This column gives a
   strict per-payment recording order (R4).
5. **Copies `FailureReason`** into `LastError` where `LastError` is null, then drops `FailureReason`.
6. **Makes `NextAttemptAt` NOT NULL**, using `COALESCE("NextRetryAt", "CreatedAt")`.
7. **Replaces the indexes**:
   - recreates the partial due index as `IX_payment_outbox_due`, on `NextAttemptAt` where
     `Status = 'Pending'`;
   - adds `IX_payment_outbox_payment_sequence` on (`PaymentId`, `Sequence`).

The `Down` migration reverses these steps, which is safe because no data is lost.

**Rationale**: this keeps a single outbound mechanism (FR-009, Constitution VI). Rows that are in
flight carry over unchanged, so a `PendingRetry` row becomes `Pending` and is published by the
relay. Nothing is lost or published twice by the switch-over. History is kept for `Resolved` and
`Exhausted` rows.

**Alternatives**:
- *Keep the old names*: "dead letter" would then describe every event, which is misleading for
  operators.
- *A new table plus a data copy* (option B): rejected by the user.

## R2. Write path: the Service records, never publishes

**Decision**:
- Add a new Service port, `IPaymentOutbox`, with three methods:
  - `AddProcessedAsync(PaymentProcessed)`
  - `AddFailedAsync(PaymentFailed)`
  - `AddRefundedAsync(PaymentRefunded)`

  It is implemented in Infrastructure as `PaymentOutbox`, over the scoped `PaymentsDbContext`.
  For each call it builds the integration event: a new `eventId`, the same fields as today, and
  serialisation that moves from `PaymentEventPublisher`. It then adds a `Pending` entry with
  `NextAttemptAt = RecordedAt = now` and calls `SaveChangesAsync`.
- Both handlers call it **inside** the existing US-05 `IOrderUnitOfWork` transaction, after the
  payment save and before `CommitAsync`. The state change and its entry therefore commit or roll
  back together (FR-001).
- `IPaymentEventPublisher` is **deleted**. No Service code can reach Kafka (FR-002,
  Constitution I).
- `PaymentEventPublisher` keeps only `IRawEventPublisher.PublishRawAsync`, which the relay uses,
  and loses its dead-letter code.

**Rationale**: the per-order transaction already exists, so the outbox write adds one insert to
it. Serialising when the entry is recorded means the stored payload is exactly what is published
(Constitution I).

## R3. Relay: evolve the US-03 worker

**Decision**: rename and extend the US-03 components.

- **Renames**:

  | US-03 name | US-07 name |
  |---|---|
  | `DeadLetterRetryWorker` | `OutboxRelayWorker` |
  | `DeadLetterRetryProcessor` | `OutboxRelayProcessor` |
  | `DeadLetterRetryPolicy` | `OutboxRetryPolicy` |
  | `DeadLetterRetryOptions` | `OutboxRelayOptions`, section `OutboxRelay` |
  | `IPaymentDeadLetterRepository` / `PaymentDeadLetterRepository` | `IPaymentOutboxRepository` / `PaymentOutboxRepository` |
  | `PaymentDeadLetterEntity` | `OutboxEntryEntity` |
  | `DeadLetterStatus` | `OutboxStatus` |

  The folder `DeadLetters/` becomes `Outbox/`.
- **Settings**:

  | Setting | Default |
  |---|---|
  | `PollIntervalMs` | 250 (was `IntervalMs` 30 000) |
  | `BatchSize` | 100 (was 20) |
  | `BaseDelayMs` | 5 000 |
  | `MaxDelayMs` | 600 000 |
  | `MaxRetries` | 8 |

- **Cycle**: one transaction per entry, as today.
  1. Claim (R4).
  2. `PublishRawAsync`, unchanged: stored topic, key and payload.
  3. On success, set `Published` and `PublishedAt`.
  4. On failure, apply the backoff, then `Exhausted` at the maximum.
  5. Commit.

  The processor keeps claiming until nothing is due or `BatchSize` is reached. The worker runs a
  cycle every `PollIntervalMs`, starting immediately (`Task.Yield`, never blocking startup).

**Latency (FR-006, SC-002)**: with a 250 ms poll and a healthy broker, the worst case is about
250 ms plus one produce round trip, well inside 1 s at p95 and 2 s at most. When idle, the
cost is four indexed queries per second per instance, using the partial index. That is
negligible.

**Alternatives**:
- *An in-process wake-up signal after commit*, with a slow poll as backstop. It gives lower
  latency, but needs a cross-scope notification. It is not needed to meet the bound and can be
  added later.
- *`LISTEN/NOTIFY`*: needs a dedicated connection, which is more moving parts.

## R4. Per-payment ordering and claiming

**Decision**: the claim query, with `FOR UPDATE SKIP LOCKED` and `LIMIT 1`:

```sql
SELECT * FROM payment_outbox o
WHERE o."Status" = 'Pending' AND o."NextAttemptAt" <= @now
  AND NOT EXISTS (
    SELECT 1 FROM payment_outbox e
    WHERE e."PaymentId" = o."PaymentId" AND e."Sequence" < o."Sequence"
      AND e."Status" <> 'Published')
ORDER BY o."Sequence"
LIMIT 1
FOR UPDATE SKIP LOCKED
```

- **Ordering**: an entry is eligible only when every earlier entry for its payment is
  `Published`. Exhausted earlier entries block later ones too (spec US3 #2).
- **Two instances**: one instance may hold entry 1 of payment P locked while it publishes. A
  second instance skips entry 1 because of `SKIP LOCKED`. It also excludes entry 2, because the
  `NOT EXISTS` reads entry 1's committed status, which is still `Pending`. So entry 2 is never
  published first (FR-005, FR-007).
- **No head-of-line blocking**: other payments are unaffected, because ordering is per payment
  (FR-007).
- **Reporting**: when an entry becomes `Exhausted`, the Error log line also states how many later
  entries for the same payment are now blocked (US3 #2).

**Rationale**: Kafka keeps order within a partition, and the key is the payment id. So once
entries are published in sequence, consumers see them in order.

## R5. Crash and duplicate semantics

A crash after `ProduceAsync` but before the commit leaves the entry `Pending`. It is published
again with the same `eventId`. This at-least-once behaviour is accepted (spec, Constitution VI).

The producer keeps `MessageTimeoutMs = 10 000`, so a broker outage fails an attempt within
10 s and the row lock is held at most that long.

## R6. What operators do with `Exhausted` entries

**Decision**: re-queue an entry by setting `Status = 'Pending'`, `RetryCount = 0` and
`NextAttemptAt = now()`. This is documented in `docs/outbox.md`, which replaces
`docs/dead-letter-retry.md`. Later entries for the same payment follow automatically, in order.

## R7. Tests

**Unit tests** (`Infrastructure.Tests`):
- rename the policy, processor and worker tests;
- the processor tests use a fake repository, so ordering is tested in integration.

**Service unit tests**: `Mock<IPaymentEventPublisher>` becomes `Mock<IPaymentOutbox>`. Assert
the following order:
1. the payment save;
2. the outbox add;
3. the commit.

Assert also that nothing is published.

**Integration tests** (PostgreSQL):
- Replace `FakePaymentEventPublisher` with an `OutboxReader` helper. It reads `payment_outbox`
  and maps rows to the domain events, so existing assertions keep their shape.
- New tests:
  - atomicity: when the commit fails, neither the payment nor the entry exists;
  - the claim respects per-payment order, `Exhausted` blocks later entries, and two concurrent
    claimers never take the same entry or break the order;
  - the migration converts rows of each status, backfills `EventId` and `Sequence`, and
    carries over a `PendingRetry` row as `Pending`.

**Component tests** (Kafka + PostgreSQL), with the relay hosted next to the consumers:
- **Crash recovery**: run with the relay *not* hosted (the process is "stopped"), then host it,
  and check the event is delivered once.
- **Latency**: 20 orders, p95 under 1 s.
- **Ordering**: the processed entry fails because the broker is unreachable, then the payment
  is refunded. Once the broker is back, the two messages arrive in order.

Existing flow tests also host `OutboxRelayWorker`.
